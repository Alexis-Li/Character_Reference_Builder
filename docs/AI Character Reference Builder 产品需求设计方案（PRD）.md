# AI Character Reference Builder 产品需求设计方案

**文档版本：** V0.1  
**文档阶段：** 前期产品需求定义  
**产品类型：** 面向 3D 角色/服装建模的节点式 AI 参考图生成工具  
**暂定名称：** AI Character Reference Builder

---

## 1. 产品概述

本产品是一套面向 3D 角色美术生产流程的节点式 AI 参考图处理工具。

产品接收原画设计师提供的角色或服装设计图，将原始设计图转化为更适合 3D 建模使用的标准化参考资料，包括：

- 标准 A-pose 角色参考；
- 多角度角色/服装视图；
- 基于建模需求的服装部件拆分方案；
- 指定部件的精确区域提取；
- 各部件独立多视图及细节参考；
- 原画与生成结果之间的一致性检查；
- 标准化项目输出。

产品采用类似 ComfyUI 的节点式工作流，但节点不暴露扩散模型、采样器、VAE 等底层生成参数，而是直接对应 3D 美术生产动作，例如“服装分析”“A-pose”“多视图”“拆件”“框选部件”“生成部件参考”。

产品只使用云端 AI 模型，不考虑本地模型推理。

---

# 2. 产品目标

产品需要解决当前 AI 辅助 3D 建模中的三个核心问题。

### 2.1 将普通角色原画转换为可建模参考

原画设计通常服务于视觉设计而不是建模，因此可能存在：

- 非标准姿势；
- 身体或服装互相遮挡；
- 缺少侧面、背面信息；
- 透视夸张；
- 局部结构表达不完整。

产品需要利用多模态模型补全这些信息，并将角色整理成更适合 3D 建模观察的标准参考。

### 2.2 将复杂角色设计拆解为适合 AI 单独处理的部件

复杂角色整体直接生成时，AI 容易出现：

- 装饰遗漏；
- 结构混淆；
- 左右不一致；
- 前后关系错误；
- 小型附件变形；
- 原设计被重新设计。

因此产品需要先从“3D 建模逻辑”理解服装结构，再拆成相对独立的建模单元，例如：

外套、内搭、衣领、袖子、腰带、裙摆、肩甲、挂件、鞋、金属扣件等。

之后分别生成这些部件的建模参考。

### 2.3 尽可能保持与原画一致

产品的目标不是重新设计角色，而是“补全设计信息”。

AI 可以推测原画中没有展示的信息，但不能无约束地重新设计已有部分。

所有生成节点都应以：

**保持原设计 > 补充不可见信息 > 美化画面**

作为优先级。

---

# 3. 目标用户

第一阶段主要服务于：

- 3D 角色模型师；
- 3D 服装模型师；
- 游戏角色美术；
- 需要将 2D 角色设计转化为 3D 资产的个人或小型团队。

产品暂不定位为通用 AI 绘图软件。

---

# 4. 典型使用场景

### 场景 A：只有普通角色立绘

输入：

角色正面或 3/4 角度设计图。

输出：

A-pose → 多视图 → 服装结构分析 → 部件拆分 → 部件参考图。

### 场景 B：已经有 A-pose 原画

跳过 A-pose 标准化，直接：

A-pose → 多视图补全 → 拆件 → 部件参考。

### 场景 C：已有部分多视图

用户可同时输入正面、侧面、背面等多张设计图。

系统应将这些图片作为共同设计依据，而不是重新生成已有信息。

### 场景 D：只需要处理某个部件

例如只需要处理：

- 鞋；
- 腰带；
- 肩甲；
- 裙摆；
- 发饰。

用户可以直接框选目标部件，不运行完整角色工作流。

---

# 5. 产品核心流程

标准工作流定义为：

**原画输入  
→ 原画/服装理解  
→ A-pose 标准化  
→ 多视图生成  
→ 建模拆件规划  
→ 部件区域确认  
→ SAM 精确分割  
→ 部件独立参考生成  
→ 一致性检查  
→ 人工选择/修正  
→ 输出**

所有阶段均允许用户插入节点、修改提示词或跳过不需要的阶段。

产品不强制用户运行固定流程。

---

# 6. 节点系统设计原则

节点系统参考 ComfyUI 的连接逻辑，但节点层级应明显高于 ComfyUI。

例如不出现：

`Checkpoint Loader → CLIP → KSampler → VAE Decode`

而是：

`原画 → A-pose → 五视图 → 拆件 → 外套参考图`

每个节点代表用户能够理解的生产任务。

节点应支持：

- 自由连接；
- 分支；
- 合并；
- 重复执行；
- 单节点重新执行；
- 上游结果缓存；
- 节点禁用；
- 节点组；
- 工作流保存；
- 工作流模板；
- 输入输出预览。

---

# 7. 基础数据类型

为了保证不同节点能够自由组合，产品至少需要支持以下逻辑数据类型：

| 类型 | 用途 |
|---|---|
| Image | 单张图片 |
| Image Set | 多张相关参考图 |
| Mask | 部件遮罩 |
| Region | 框选/指定区域 |
| Text | 自然语言描述 |
| Design Data | 角色及服装结构信息 |
| Part Data | 单个建模部件信息 |
| Part Set | 多个部件集合 |
| View Set | 多角度视图集合 |
| Review Result | AI 检查结果 |

用户不需要直接理解底层数据结构，但节点之间应通过这些统一类型交换信息。

# 8. 核心节点需求

## 8.1 Image Input / Reference Input

负责输入原始设计资料。

需要支持：

- 单张图片；
- 多张参考图；
- 主参考图与辅助参考图区分；
- 图片备注；
- 参考图角色定义；
- 用户指定某张图的视角。

例如：

`Front`
`Side`
`Back`
`Detail`
`Style Reference`

多张原画需要被系统视为同一设计项目，而不是互相独立的图片。

---

# 9. Natural Language / Prompt 节点

这是一个通用节点。

用户可以在工作流任意位置插入自然语言要求，例如：

> 保持原设计，不增加新的装饰。

或：

> 裙摆一共有三层，不允许合并。

或：

> 重点补全背部腰带和肩甲连接关系。

该节点可以连接到：

- 服装分析；
- A-pose；
- 多视图；
- 部件拆分；
- 图片生成；
- 一致性检查。

这样用户不需要进入每个 AI 节点内部修改复杂 Prompt。

应支持保存常用 Prompt Preset。

Node Banana 已经具有 Prompt、Prompt Constructor、LLM 驱动动态 Prompt 等类似节点，可以优先复用或改造这一体系。

---

# 10. Design / Garment Analyzer

这是产品最核心的专用节点之一。

输入：

- 原画；
- 其他设计参考；
- 用户补充说明。

输出：

结构化角色设计信息。

至少需要识别：

### 角色整体

- 身体比例；
- 服装主要轮廓；
- 设计风格；
- 对称/非对称关系。

### 服装层级

例如：

角色  
→ 外套  
→ 内搭  
→ 腰带  
→ 裙摆  
→ 鞋

并进一步理解：

外套  
→ 衣领  
→ 袖子  
→ 袖口  
→ 肩部装饰

### 结构关系

例如：

- A 覆盖 B；
- A 固定在 B 上；
- A 位于 B 外层；
- A 左右对称；
- A 只有角色左侧存在。

### 建模建议拆件

AI 应从“3D 模型制作”的角度提出拆件方案，而不是单纯做图像语义分类。

这是目前搜索到的社区项目中没有成熟通用方案可以直接复用的部分，应被视为本产品的核心差异化能力。

---

# 11. A-Pose Normalize

负责将非标准角色原画转换为适合建模参考的 A-pose。

节点应允许选择：

### 标准模式

优先获得标准、左右清晰、身体无遮挡的 A-pose。

### 保守模式

优先保持服装结构。

当标准姿势调整可能造成服装大幅重新解释时，应允许姿势稍微偏离标准 A-pose。

节点输出不能只是一张“看起来像原角色”的新图，而应尽可能继承：

- 身体比例；
- 服装长度；
- 部件数量；
- 配色；
- 图案；
- 装饰位置；
- 层级关系。

---

# 12. Turnaround Generator

生成角色或服装多视图。

需要支持预设：

- 3 视图；
- 5 视图；
- 6 视图；
- 8 视图；
- 自定义角度。

第一版推荐默认：

**Front / Front 45° / Side / Back 45° / Back**

用户可以指定：

- 角色不动，相机旋转；
- 固定相机高度；
- 尽量一致的焦距；
- 尽量一致的身体比例；
- 中性背景；
- 弱化戏剧化光照；
- 强调建模可读性。

社区中的 `ComfyUI-H3-ContactSheet` 已经验证了“单张参考 → 五个协调视角”的工作流设计；`ComfyUI-MiniMax-H3-Edit` 也包含 Character Sheet 与连续相机视角逻辑。

由于本产品明确不运行本地模型，这两个项目不作为运行依赖，但其多视图定义、视角组织和 Character Sheet 产品逻辑可以直接作为设计参考。

---

# 13. Part Planner

负责把 Design Analyzer 输出的服装结构进一步转化为“AI 生成任务”。

例如：

AI 识别：

`Coat`
`Collar`
`Sleeve`
`Belt`
`Buckle`

Part Planner 需要进一步判断：

### 是否独立生成

外套：

需要完整多视图。

衣领：

可能只需要局部结构图。

左右袖：

如果完全对称，可以只生成一侧。

腰带：

适合独立物件生成。

金属扣：

适合局部放大参考。

### 是否需要进一步拆分

例如裙子可能进一步拆成：

- 外层裙摆；
- 内层裙摆；
- 腰封；
- 挂饰。

用户必须能够手动：

- 新增部件；
- 删除部件；
- 合并部件；
- 重命名；
- 修改父子关系。

AI 给出的是建议，而不是不可修改的最终决定。

---

# 14. Region / Box 节点

用于人工告诉系统：

**“我要的是这里。”**

这是整个产品非常重要的人机协作节点。

至少支持：

### Box

矩形框选目标区域。

### Point

在目标物体上添加正向提示点。

### Exclude Point

明确指出某部分不属于目标。

后续版本可以增加：

### Brush

用户简单涂抹目标区域。

Region 节点需要同时传递：

- 图片；
- 区域；
- 部件名称。

例如：

`Picture + Region + "left shoulder armor"`

送入 Segmentation 节点。

Node Banana 本身已经具有全屏 Image Annotation Editor，可进行矩形、圆形、箭头、自由绘制和文字标记，因此框选/标注界面没有必要从零开发。

---

# 15. Segmentation / SAM 节点

负责将用户或 AI 指定的部件转换为精确 Mask。

输入可以包括：

- 图片；
- 文本部件名称；
- Box；
- Point；
- 初始 Mask。

输出：

- Mask；
- 裁切图片；
- Alpha 图片；
- Bounding Box。

本产品不运行本地 SAM。

云端 `fal.ai` 已经提供 SAM 3 API，并且原生支持文本提示、Point Prompt、Box Prompt、多 Mask 输出和 Bounding Box，因此这部分没有必要自行部署或重新实现模型能力。

社区 `ComfyUI SAM3` 已经验证了文字分割、独立 Mask、组合 Mask、Crop、SEGS 等节点设计，其交互和输出结构可以作为产品节点设计参考，但不作为本产品本地运行依赖。

---

# 16. Part Reference Generator

输入：

- 原始设计图；
- 多视图；
- 部件 Mask；
- Part Data；
- 用户 Prompt。

负责单独生成该部件的建模参考。

需要支持不同 Reference Template。

例如：

### Garment Turnaround

适用于：

- 外套；
- 上衣；
- 裙子；
- 裤子。

### Object Turnaround

适用于：

- 腰带；
- 鞋；
- 包；
- 武器挂件；
- 护甲。

### Detail Sheet

适用于：

- 衣领；
- 金属扣；
- 接缝；
- 装饰件。

节点不应要求用户重新手动描述整个角色。

上游 Design Data 和 Part Data 必须自动作为上下文传入，避免每个节点重复编写 Prompt。

---

# 17. Occlusion Recovery

用于恢复原画中被遮挡的部件。

典型情况：

- 手挡住腰带；
- 头发挡住衣领；
- 武器挡住裙摆；
- 外套挡住内搭；
- 身体角度导致某部分完全不可见。

系统需要结合：

- 已有多视图；
- 原画设计；
- 对称结构；
- 同类部件；
- 用户说明；

生成合理补全。

补全结果必须标记为“AI 推测内容”，区别于原画明确存在的信息。

---

# 18. Symmetry / Mirror Assist

用于左右对称结构。

系统应知道：

- 哪些部件完全对称；
- 哪些只是基本结构对称；
- 哪些左右设计不同。

对于完全对称部件，可以复用一侧设计作为另一侧约束，以减少不必要的 AI 重新设计。

---

# 19. Reference Lock

用于明确指定后续生成过程中不能随意改变的信息。

支持锁定：

- 主轮廓；
- 配色；
- 图案；
- 部件数量；
- 装饰位置；
- 长度比例；
- 层级关系；
- 左右关系。

Reference Lock 可以由 AI 根据原画自动生成，也允许用户手工修改。

---

# 20. Consistency Checker

用于比较生成结果与原始设计。

检查重点不是画面质量，而是设计一致性。

至少包括：

### 结构检查

- 是否缺少部件；
- 是否新增部件；
- 部件数量是否变化；
- 层级是否错误。

### 形状检查

- 长短比例变化；
- 轮廓变化；
- 宽度变化；
- 左右结构变化。

### 视觉信息检查

- 配色；
- 图案；
- 材质属性；
- 装饰位置。

### 多视图一致性

检查同一物体在不同视图之间是否出现：

- 长度变化；
- 数量变化；
- 左右翻转错误；
- 前后结构矛盾。

输出应该是“发现的问题”，而不是简单给一个分数。

例如：

> 背面图中腰带宽度明显比正面增加。

> 左肩有两个金属扣，侧面图只保留一个。

> 原图裙摆为三层，生成图被合并成两层。

---

# 21. Compare / Select

用于比较多个生成结果。

用户可以：

- 并排查看；
- 放大；
- 同步缩放；
- 指定最终选择；
- 将选中的结果继续送往下游。

Node Banana 已有 Image Compare 和 Output Gallery，可以优先复用这部分能力。

---

# 22. Approval Gate

用于在自动工作流中插入人工确认。

例如：

`A-pose`
→ `Approval`
→ `Turnaround`

只有用户确认后才继续。

适合放在：

- A-pose 后；
- 多视图后；
- 拆件规划后；
- 部件最终生成后。

这样可以避免某一步出现设计偏差后，错误继续传播到整个工作流。

---

# 23. Provider 系统

模型供应方式必须和工作流节点解耦。

产品默认使用：

### Primary Provider

**ChatGPT OAuth**

日常优先消耗用户已有 ChatGPT 账号能力。

### Fallback Provider

**OpenAI API**

当 OAuth：

- 不可用；
- 达到限制；
- 请求失败；
- 某项能力 OAuth 不支持；

时允许用户切换到 API。

第一版至少需要提供：

`Prefer OAuth`

`OAuth Only`

`API Only`

三种模式。

节点可以继承项目默认 Provider，也允许高级用户单独覆盖某个节点。

---

# 24. ChatGPT OAuth 复用需求

OAuth 层不建议自行从零设计。

已有多个 Agent 项目证明 ChatGPT/Codex OAuth 可以被抽象为独立 Provider。

OpenCode 的 `opencode-openai-codex-auth` 已实现 ChatGPT OAuth、Token 保存、自动刷新和错误处理。

Hermes 也将 OpenAI Codex 作为独立 Provider，支持 ChatGPT device-code OAuth，并能够导入 Codex CLI 的现有登录凭据。

更直接可评估复用的是：

### openai-oauth

该项目已经封装：

- Sign in with ChatGPT；
- OAuth 凭据；
- OpenAI SDK Adapter；
- OpenAI-compatible 接口；
- GPT Image 2 图像生成；
- GPT Image 2 图像编辑。

项目采用 Apache-2.0 License。

因此它应作为第一优先级 OAuth 复用候选。

### chatgpt-bridge

该项目提供本地 OpenAI-compatible Proxy，并支持通过 ChatGPT OAuth 调用文本、视觉和 GPT Image 2。

项目采用 MIT License。

可作为：

- 第二候选；
- 参考实现；
- 独立兼容层。

产品不应把 OAuth 逻辑写死在具体 AI 节点中。

---

# 25. Provider Fallback 行为

OAuth 与 API 的切换原则：

默认情况下：

**OAuth 优先。**

如果 OAuth 本次请求失败，系统应明确说明失败原因，并根据用户设置：

- 自动切 API；
- 或等待用户确认。

不能出现：

OAuth 请求失败但用户不知道，系统静默产生 API 消费。

用户需要能够看到当前节点实际使用：

- Provider；
- Model；
- OAuth / API；
- 是否发生 Fallback。

---

# 26. Workflow Preset

产品应自带若干官方工作流模板。

第一阶段至少需要：

### Character Full Pipeline

完整：

原画 → A-pose → 多视图 → 拆件 → 部件生成。

### Turnaround Only

原画 → 多视图。

### Garment Decompose

原画 → 分析 → 拆件 → Mask。

### Part Reference

单独部件 → 多视图。

### Detail Recovery

局部区域 → 遮挡恢复/细节补全。

Node Banana 已支持工作流 JSON 保存/加载以及可复用工作流，可以直接继承这一产品模式。

---

# 27. 项目管理

一个角色应被视为一个 Project，而不是一组散乱图片。

Project 至少保存：

- 输入原画；
- 补充参考；
- 当前工作流；
- Design Data；
- Part List；
- Masks；
- 多视图；
- 各部件结果；

# 32. 需要本产品自行设计的核心能力

社区已有项目可以解决大量基础设施问题，但以下能力不能简单依赖现成项目。

### 3D 建模向 Design Analyzer

AI 不只是识别图片内容，而是理解：

“这个设计应该怎样拆成 3D 模型。”

这是产品最核心的专业逻辑。

### Part Planner

决定：

什么需要独立生成、什么应该合并、什么需要细节图。

### Reference Lock

把原画中的关键设计转换成后续生成必须遵守的约束。

### Consistency Checker

不是普通图片质量评价，而是针对角色设计一致性进行审核。

### 服装部件之间的关系管理

例如：

- 父子关系；
- 层级；
- 对称；
- 左右；
- 覆盖关系；
- 所属角色。

这些应成为产品的主要差异化价值。

# 35. MVP 成功标准

第一版产品是否成功，不以“AI 图片是否漂亮”为判断标准。

应该看它是否真正减少 3D 模型师整理参考图的工作量。

成功标准包括：

### 从单张角色图能够得到可使用的 A-pose。

### 能够得到结构基本一致的角色多视图。

### 能够给出合理的 3D 建模拆件列表。

### 用户可以通过框选快速纠正 AI 的拆件范围。

### 能够把指定服装部件独立提取并生成进一步参考。

### 用户不需要为每个部件重新解释整个角色设计。

### 后续部件生成能够继承原角色上下文。

### 系统能够发现明显的多视图和原画一致性错误。

### 大部分日常请求可以通过 ChatGPT OAuth 完成。

### OAuth 不可使用时能够切换 OpenAI API，而无需改变整个工作流。

# 36. 产品核心价值

本产品真正需要建立的不是另一套 AI 图片生成界面，而是一层位于“角色原画”和“3D 建模”之间的结构化工作流。

现成项目已经能够解决：

**节点编辑器 + Prompt + 图片标注 + 云端模型调用 + OAuth + SAM 分割 + 图片对比**

因此没有必要重新开发这些通用能力。

产品开发的重点应集中在：

**如何理解一个角色设计、如何按照 3D 制作逻辑拆解它、如何把原画信息持续传递给后续生成、以及如何判断生成结果有没有偏离设计。**

这四项能力决定产品是否真正适合 3D 角色美术生产，而不是又一个通用 AI 节点工具。
