# 最小闭环验证方案与执行结果

日期：2026-09-10。依据：[产品需求](../product-requirements.md)。

**结论：工程可行性已有实测证据，可以启动受控原型开发；完整生产闭环尚未验收通过。** Node Banana 可作为二次开发起点，但多参考传递、候选选择和失败回退必须修改。真实角色质量、账户可用性及总成本尚未验证，不以模拟出图或构建成功代替。

## 1. 验证目标与边界

最小路径：**导入原画 → 框选／文字指定部件 → 首次参考生成 → 指定修改 → 比较并人工选择 → 保存重开 → 导出。**

先验证单个部件，不要求先搭完整拆件、A-pose 或角色三视图链。不在本轮扩展视频、3D 生成、无人值守批处理和 SAM；SAM 是独立可选能力。

分开记录三个层次：

1. 工程行为：输入传递、版本保留、失败处理、文件落盘与重开。
2. 云端能力：实际账号接受请求、参考利用、编辑效果和费用。
3. 美术可用性：模型师是否接受参考用于建模，推测是否清楚且可纠正。

当前完成第一层的候选评估；第二、三层缺少用户指定的真实原画、可调用 Provider 和费用范围。已请求这些信息，本轮未收到。进程环境中的 `OPENAI_API_KEY`、`GEMINI_API_KEY`、`GOOGLE_API_KEY` 均未配置；没有扫描或读取其他应用私有凭据，也没有把 Codex 内置生成能力当成独立产品接口。

### 3.1 七项工程探针

| ID | 输入／操作 | 实际结果 | PRD 判断 |
| --- | --- | --- | --- |
| P01 | 原图和部件提示 → 模拟生成 → 连接优化节点，传原图及首轮结果 | 两张图均到达客户端生成请求；上游候选不变、优化结果独立 | 客户端数据流通过；不证明服务端或真实模型使用了全部参考 |
| P02 | 已有输出，未配备用，重跑遇网络错误 | 请求一次，保留已有输出 | 此条件通过 |
| P03 | 两个分支输出 → 实际 `saveWorkflow` JSON 序列化 → `loadWorkflow` | 两张输出保留，未发生成请求 | 分支图片重载通过；不代表独立人工选择、审核或历史图像全量保留 |
| P04 | 调用上游 OpenAI 适配器，输入原图和保留视图，截获 multipart | 实际只有 1 张 image；期望 2 张 | **不通过：参考静默丢失** |
| P05 | 主请求网络响应丢失，配置不同备用模型 | 实际调用 2 次；期望不自动发第二次 | **不通过：状态未知仍回退** |
| P06 | 已有输出，主请求和备用请求都失败 | 当前输出变为 null | **不通过：失败清空可用结果** |
| P07 | 已有当前输出，成功重跑 | 当前输出被新结果直接替换 | **不通过：缺少与运行输出分离的人工选定结果** |

P07 使用当前输出作为已有选择的代理来验证需求；上游本身没有本项目所需的独立选定结果契约，不能把节点选中状态或轮播索引当作该契约。节点历史最多保留 50 条元数据，图像历史与落盘另有条件，需由项目资产与版本机制补齐。[生成执行器](https://github.com/shrimbly/node-banana/blob/5c0e0ae6150f29a6de819f8d6f1dedba15151f7c/src/store/execution/nanoBananaExecutor.ts#L182)

### 3.2 失败的原因与影响

- **多参考丢失：** OpenAI handler 明确取 `input.images[0]`。前端能接多张图不代表端到端支持多参考；必须修正适配器并测试请求形态。[源码](https://github.com/shrimbly/node-banana/blob/5c0e0ae6150f29a6de819f8d6f1dedba15151f7c/src/app/api/generate/providers/openai.ts#L62)
- **回退过宽：** 除 abort 和相同模型外，一般错误都会尝试备用，辅助函数没有预算或“上游是否执行”判定；切换时还清空输出。[源码](https://github.com/shrimbly/node-banana/blob/5c0e0ae6150f29a6de819f8d6f1dedba15151f7c/src/store/execution/runWithFallback.ts#L54)
- **保存测试跨平台问题：** 路由测试使用 `/test/dir`、`/etc` 等路径；Windows 上 `path.resolve(input) !== input` 导致提前失败。真实原生绝对路径读写通过，但 `E:/…` 形式实测被同一判断误拒绝。应修复合法路径归一化并保留真正的越界拒绝。[校验源码](https://github.com/shrimbly/node-banana/blob/5c0e0ae6150f29a6de819f8d6f1dedba15151f7c/src/utils/pathValidation.ts#L23)

没有为了让基线通过而修改上游生产代码，也没有把失败测试改成预期成功。重跑探针在当前快照返回非零是如实报告需求缺口。

## 4. 真实模型验证执行协议

待输入齐备后按以下固定样本执行，不能先看结果再修改通过条件。样本清单保存在本地角色项目中，包含输入哈希、目标部件、已有事实、允许推测范围和审核人。

| 样本 | 最小资料 | 首次生成与修改要求 | 重点检查 |
| --- | --- | --- | --- |
| Q01 独立可见部件 | 一张原画，清晰鞋／护甲／腰带 | 文字指定；随后修正一处细节 | 目标归属、数量、轮廓、配色、连接位置 |
| Q02 部件与手重叠 | 一张存在遮挡的原画及框选 | 仅生成指定部件，补全遮挡 | 排除手及邻物；不可见结构标为推测 |
| Q03 已有背面依据 | 同角色正面、背面及非对称细节 | 只优化背面，正面保持原文件 | 确实利用背面依据，左右关系正确，正面哈希不变 |
| Q04 缺失背面 | 与 Q03 对应的正面，故意不提供背面 | 生成必要背面参考 | 不声称知道未提供设计，明确推测；用于与 Q03 对照 |

每个已获准 Provider 对同一资料执行一次首轮生成和至多两轮人工指定优化。这个上限是本次可行性实验的调用上限，不限制产品以后的迭代次数；扩大实验需先更新费用范围。完整矩阵至多为“4 个样本 × 3 次调用 × Provider 数量”，生成张数、输入量和真实价格仍需运行前计算；达到调用或费用任一上限即停止，不静默换 Provider。

先完成一个 Provider 的 Q01，再扩展 Q02–Q04；确认首个组合值得继续后，才验证第二个兼容 Provider 的替换与混用。订阅入口失败应单列，不用 API 成功替代。

逐次记录：资料及版本、目标部件／视图、有效约束、修改范围、实际 Provider／模型／授权类型、开始结束时间、请求状态、可得 usage／费用、输出文件与哈希、人工差异判断。不能从缺失 usage 或第三方补零推定免费。

**通过条件：** 每个样本都能在本轮约定调用／费用范围内获得模型师认为可继续建模的选定参考；已有设计的重大偏差已修正，或被明确记录并由模型师接受。所有输出都有依据、推测和审核状态；局部优化不覆盖保留视图；保存重开可继续优化，导出资产与选定版本一致。若仅部分样本通过，收窄支持范围或换模型后重新验证失败场景，不宣称全矩阵通过。

人工整理同一部件的耗时需记录基线，分开报告操作时间、等待时间和总成本。没有人工基线时只能报告绝对数据，不能声称效率提升。并非本次所有指标都已具备数值结果。

## 5. 继续执行所需输入

1. 用户明确指定可用于云端测试的原画路径和目标部件，至少能开始 Q01；后续补齐正背面与遮挡样本。
2. 可用 Provider／模型及认证途径。优先由用户在应用设置或环境配置凭据，文档和对话不记录秘钥；OAuth 需确认适用账户路径。
3. 新增 API 费用是否允许，以及本轮金额和调用范围；未指定时不新增付费调用。
4. 模型师对结果的判断；自动一致性检查可辅助，不能代替人工生产验收。
