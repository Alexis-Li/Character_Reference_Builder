# Issue、PR 与归档流程

本项目使用 [GitHub Issues](https://github.com/Alexis-Li/Character_Reference_Builder/issues) 管理任务，默认集成分支为 `main`。在本项目 checkout 中使用已认证的 `gh`，命令显式指定 `--repo Alexis-Li/Character_Reference_Builder`；使用 GitHub 连接器或 API 时也显式指定相同仓库标识。

**PRs as a request surface: no.** PR 不作为需求分诊入口，但承载实现交付与代码审核。Issue 和 PR 共用编号空间，处理裸编号前确认对象类型。Skill 所说的“发布到 issue tracker”指创建 GitHub Issue，“读取相关 ticket”指读取 Issue 正文及相关评论。

## 从需求到完成

1. **界定任务。** 阅读完整产品需求、Issue 正文及全部评论，列出可观察的验收条件、排除项和依赖，并按 AC 选择[证据类型](#验收证据与真实样本实验)。复杂任务使用稳定的 `AC-01` 等编号，编号不复用；旧任务可引用原文。区分实现建议与已同意要求，不自行扩大原型验收。简单本地修正无需为了流程新建 Issue。
2. **选择交付范围。** 按下节选择分支与交付方式，并完成[开发前设计](#开发前设计)。切换前检查并保留未提交工作；并行写入使用隔离 checkout 和明确文件归属，不切换其他任务的工作分支。
3. **交付可审核结果。** 记录比较基线、交付 HEAD 的完整 SHA、目标分支、行为变化、实际检查和剩余缺口。PR 使用[仓库模板](../../.github/pull_request_template.md)，Issue 链接该交付；获准的直接分支交付按需用普通评论说明，不要求固定报告。未提交交付注明基线、完整 diff 与相关未跟踪文件，不能称为已审核提交。
4. **审核实际差异。** 对照验收阅读指定基线的完整 diff、调用方和测试，检查兼容性、失败恢复、资产保留、付费重试及无关变更。每次 PR 合并前必须有已发布、覆盖当前完整 HEAD 的审核结论；自测和用户的合并授权均不能替代审核。需要独立审核的任务未取得该结论时保留待审核状态。
5. **集成已审结果。** 集成前重查任务 HEAD、目标分支变化、冲突解决及受影响检查；有影响时增量复核并发布结论后再合并。核对实际集成差异与检查，将最终集成 SHA、PR、覆盖的 AC 和待验收项写入 Issue 进展评论，不在 PR 另发合并 SHA 评论；squash／rebase 后仍记录原审核范围。按下节处理已合并分支。直接分支交付也按影响检查，不能以代码已在分支上代替验收。
6. **完成任务。** 同意的 AC 已满足或由用户明确调整、阻塞发现已复验关闭、交付位于约定集成分支且相关证据仍适用后，按[归档与清理](#归档与清理)整理状态评论并显式关闭 Issue，不另发关闭评论。状态评论包含最终审核、集成结果、验收与后续事项。研究／实验按约定交付物验收，负面实验结论不等于质量通过；主线里程碑、真实 Provider／生产验收、版本发布及归档各自判断。

提交、推送、PR 创建、发布评论、合并、关闭和删除均服从当前任务授权；本文件不扩大授权。GitHub 不可用时准备本地草稿，说明未发布并保留证据，不切换任务系统，也不把本地完成写成远端已完成。

## 分支与交付边界

- 新增能力、工具或文档使用 `feature/<topic>`，修正使用 `fix/<topic>`；topic 为简短 kebab-case，从最新 `main` 建立并以 PR 合回 `main`。每个 PR 对应一个可独立审核的改动，提交按逻辑改动组织。重大工作流程调整通过 PR 交付。
- 小型措辞、拼写、链接、格式及规则／工作流／模板文字调整，在不改变代码、测试、工具、CI、打包、版本或产品决定时，直接在当前工作分支交付，不另开分支或 PR，也不要求开发报告或审核报告；没有进行中的开发分支时才直接使用 `main`。明确差异范围并完成文档检查，规模或影响不清楚时使用 PR。
- 新分支采用上述命名；既有分支名、提交及审核来源保留事实，不为统一前缀自动重命名、切换旧任务或重写共享历史。不要把其他任务的未集成改动混入本次交付。
- 仓库设置应开启 **Automatically delete head branches**，使用前核查实际状态；未知或未开启时如实报告，并在任务授权内配置，不将文档要求写成已生效事实。合并后确认远端 head 分支删除，运行 `git fetch --prune origin`；本地 worktree 干净、无人使用且分支内容已集成并可从远端恢复时，在授权内移除该 worktree 与本地 head 分支。squash／rebase 需核对实际改动，不能仅靠祖先关系判断；不使用强制删除来跳过核验。保留脏目录、未集成工作或其他会话使用的 checkout，说明下一步。

## 审核基线与验证

开发前的设计判断、审核意见处理和选测遵循以下三节；提交基线、审核发布与集成仍按本节执行。

- 已发布审核须绑定完整比较基线 SHA、HEAD SHA、具体范围及 AC／发现编号，说明结论、依据和未覆盖项。后续提交按影响增量审核与检查，结论须明确旧审核加本轮复核覆盖了哪个完整 HEAD；不能只引用旧 HEAD 的通过结论。
- 目标分支漂移和冲突解决可能使旧证据失效。判断对接口、依赖、验收和检查的影响，有影响时复核相关差异；无影响时也记录依据。复用历史结果须说明代码与前提仍适用。
- 合并命令使用 `gh pr merge <编号> --repo Alexis-Li/Character_Reference_Builder --match-head-commit <已审核完整SHA>`；连接器或 API 使用等价的预期 HEAD 条件。该条件只保护 PR HEAD，须另行核对目标分支与实际集成结果，确认无未审改动。[CLI 说明](https://cli.github.com/manual/gh_pr_merge)。
- Issue／PR 统一使用 `Refs #<编号>`，不使用自动关闭关键词（包括 `Closes`、`Fixes`、`Resolves`）；满足本项关闭条件后单独执行关闭。[GitHub 关联规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。
- 报告分别标明已实现、已审核、已集成、实机／真实 Provider 已验收、已发布和已归档。局部审核通过可以与整项待验证并存。记录审核来源；使用作者账号发布时以评论记录基线和结论，不冒充独立 GitHub approval。
- 先运行受影响测试，实现稳定后按改动完成 `npm run build`、`npm run test:run` 及相关浏览器／Windows 检查。命令和条件见 [README](../../README.md)、[验证入口](../../scripts/validation/README.md)。后续改动可能使结果失效才重跑对应检查。
- 文档改动按[文档维护检查](documentation.md#维护检查)验证；不声称存在未配置的 CI 或自动报告门禁。真实资料、Provider、账号、费用和人工判断仍需各自证据。

## 开发前设计

| 改动范围 | 实施前明确 | 记录与决定 |
| --- | --- | --- |
| 局部修复或小功能，接口与状态归属不变 | 真实调用链、修改位置、直接受影响的行为和最小有效检查；纯文档核对受影响规则、入口与模板 | 在当前任务中简述后实施，不另建文档或 Issue |
| 跨模块功能，或改变公共接口、状态／资源归属 | 复用能力、模块职责、数据／状态流、失败恢复、兼容约定和必须保留的行为 | 写入现有 Issue 或设计记录，实施前审查一次关键设计 |
| 方案依赖尚未证实的浏览器、Windows、Provider 或 ComfyUI 能力 | 哪个疑点会改变方案，以及实验的预期和停止条件 | 先用最小原型或实验消除疑点，再扩大实现；真实调用遵循[实验授权与预算边界](#验收证据与真实样本实验) |

普通实现选择自主处理；改变已同意的产品语义或重要取舍时由用户决定。已有设计足够则引用，仅长期有效的新决策进入 ADR。职责、契约和验收清楚，且没有影响方案的疑点即可实施；设计审查不额外要求独立审核者或用户审批，不替代合并前审核。

## 审核意见与修复

- 先通过代码路径、契约或复现确认审核意见，再修改实现；文档问题核对权威正文和实际命令。风格偏好及与本次改动无关的改进记为后续候选，不驱动返工。
- 修改前检查实际调用者及状态／资源所有者，在根因位置修正。复验原问题及修复直接触及的旧行为，复用仍有效的证据；涉及节点重跑、上游变更或请求失败时，核对选定结果、下游引用及额外付费请求的影响。
- 不以吞错、删除断言、放宽阈值或改写验收标准让新问题通过。原判定确有错误时给出独立依据；修复需要改变接口或状态／资源归属时，回到开发前设计。
- 同类问题到第三轮仍反复出现时，停止叠加补丁，转入根因诊断、缩小改动或重新设计；这不是放弃任务或关闭发现的条件，已确认阻断项仍然阻断。发现编号及复验状态沿用[报告规则](#报告与接手)。

## 验证范围与停止条件

- 开始时简述需要证明的行为与最小有效检查，保留项目必需检查。扩大检查须对应未覆盖的 AC、实际失败或有证据的回归风险；具体命令和适用范围以 [README](../../README.md) 与[验证脚本说明](../../scripts/validation/README.md)为准。
- 不为没有真实触发链的假设新增测试、重试、兼容层、配置或降级分支。可能误删资产、损坏项目、破坏下游引用或重复付费的可达路径保留针对性验证。
- 必需检查通过、约定验收覆盖且没有阻断项即结束验证。修复后只复测受影响部分，稳定后完成适用的构建／回归；只有后续变化可能使旧结果失效时才重跑。缺少真实 Provider 或生产证据时保留验收缺口，不能用重复模拟测试补足。
- 需要外部环境、凭据或样本的检查明确前置条件与选择入口。显式请求的检查缺少必需条件时应失败并给出补齐方法；未选中的检查记为未执行，不能以成功退出或整个套件通过声称该项验收通过。默认检查与需显式选择的真实调用检查分开，默认测试不得隐式发起付费请求。

## 验收证据与真实样本实验

每个 AC 按要证明的行为选择一类或多类证据，注明输入、预期、实际结果和未验证范围：

| 证据类型 | 能证明的范围与边界 |
| --- | --- |
| 工程测试与构建 | 数据契约、状态、失败恢复等；模拟 Provider 只证明模拟条件下的行为 |
| 浏览器／Windows／真实本地文件操作 | 实际交互、主机行为、磁盘保存、迁移、重开与导出；合成响应不能外推真实账号或模型能力 |
| 真实 Provider／账号调用 | 本轮实际入口、认证、输入输出、请求状态及可获得的 usage／费用；登录成功不等于生成或质量通过，费用未知不能写零 |
| 视觉质量／生产评审 | 对原画依据、推测、设计偏差和建模适用性的判断；记录评审者及标准，Agent 视觉判断不能写成模型师生产验收 |

各类证据不能相互替代。纯文档任务采用内容、链接、模板及场景走查，不为补齐表格运行无关产品测试或云端调用。

真实样本实验在调用前明确输入身份／哈希、目标部件和视图、设计依据与推测、预期结果、允许入口、调用次数或预算边界及停止条件。沿用已有素材外发、账号与费用授权，仅超出授权范围时再取得授权；额度耗尽、达到约定结论、结果未知需核查或授权条件不再成立时停止，不自动追加生成、重试或备用调用。

工程缺陷、模型限制、验收缺口和后续候选分别记录：资料／约束传错、资产误覆盖等实现错误属于工程缺陷；输入正确而输出不达预期属于模型限制；缺少所需证据属于验收缺口；未纳入本次范围的改进属于后续候选。按约定执行并有证据的负面结果可以完成相应实验，不强求反复付费直到出图满意，也不能写成样本质量通过或取消其他 AC。分类争议保留证据与有效决定。

验证期间保留原画依据、候选、人工选定结果及下游引用；失败、重开、重试和清理不得隐式生成、覆盖选定结果或丢失用户资产。真实素材与调用记录按用户数据保存，仓库只保留脱敏结论；不得为归档重新付费执行。

## 报告与接手

Issue 正文维护任务范围、AC、依赖与有效决定，产品需求变更同步[完整唯一正文](../product-requirements.md)。需求或决定过时，先与用户确定替代决定，再在所属正文、ADR、文档或评论原地改写，替换旧说法；未确定替代决定前沿用有效约定。文档与评论写当前事实，不附逐轮修改说明或“按要求删除”等标注。

PR 承载详细差异、审核问题与检查。进展、审核和验收用普通评论，各自记录新事实、证据及剩余缺口，不要求三类固定报告。自己的评论有错误或内容过时则原地编辑；新交付、新审核基线或新验收结果另发评论。每条新评论末尾用一至三行 `**当前状态**：…` 说明整个 Issue 的状态、下一步及责任方。仅为追赶进度，不反复改写旧状态评论；读者从最新评论接手。

只在用户要求整理或关闭 Issue 时形成一条[状态评论](#状态评论)，平时不维护常驻汇总。普通评论仍须提供其结论所需的基线、范围、证据和限制；审核遵循[审核基线](#审核基线与验证)，不因取消报告模板而省略审核内容。

- 先读取已有问题，再分配 Issue 内稳定的 `R-001` 等编号，编号不复用。说明触发、影响、证据、严重度、是否阻塞及完成条件；修复沿用编号，状态为未解决、已修复待复验、已复验关闭或不采纳（附证据／授权决定）。实施者声称修复不等于复验关闭。
- 区分已确认缺陷、待验证风险、验收缺口和后续候选；候选不经范围决策不得升级为本项阻塞。仍影响验收的分歧列入未完成事项，不能通过整理评论消除阻断项。
- 记录实际命令、环境、跳过／失败项、夹具限制和证据适用性。原画事实与推测、模拟调用与真实调用、功能路径与质量／成本验收须明确分开。

## 状态评论

整理或关闭时采用以下结构，标识中的编号替换为当前 Issue 编号。各节填实际内容，无适用内容填“无”；日期使用任务时区的 `YYYY-MM-DD`。本仓库没有状态评论生成／校验工具，由发布者核对结构、路径、事实、链接与验收结论，不调用隔壁仓库的工具。

```markdown
<!-- issue-status:v1 issue=<编号> -->
## 状态

- 状态：进行中 / 待审核 / 待验证 / 受阻 / 可关闭 / 已关闭
- 基线：完整实现、最终审核和集成 SHA；说明未完成阶段及远端可用性
- 更新日期：YYYY-MM-DD

### 简介
### 相关提交
### 已完成
### 未完成
### 开发边界
### 决定
### 验收证据
### 下一步
```

简介给出任务目的和当前结论；相关提交链接 PR、完整 SHA、用途及最终审核。已完成／未完成按 AC 或发现编号记录结果、证据、缺口和完成条件。开发边界说明包含、排除及已移交事项；决定链接现役需求或 ADR。验收证据按本项目四类证据记录受测基线、环境、输入身份、预期、实际结果与未验证范围，区分本轮执行、历史复核及源码推断。下一步列具体行动与责任方，完成则填“无”。状态与下一步承担整体状态收尾；仅整理不算重跑验证。

## 安全发布与常用命令

```powershell
gh issue view <编号> --repo Alexis-Li/Character_Reference_Builder --json number,title,body,labels,comments,state
gh issue list --repo Alexis-Li/Character_Reference_Builder --state open --json number,title,labels,state
gh api --paginate repos/Alexis-Li/Character_Reference_Builder/issues/<编号>/comments
gh pr view <编号> --repo Alexis-Li/Character_Reference_Builder --json number,title,body,baseRefName,headRefOid,state
gh pr diff <编号> --repo Alexis-Li/Character_Reference_Builder
```

- 完成授权内的写操作时，Issue 创建／评论使用 `gh issue create`／`gh issue comment <编号>`，PR 创建使用 `gh pr create --base <目标分支>`，均加显式 `--repo` 和 `--body-file <草稿>`。标签通过 `gh issue edit` 的 `--add-label`／`--remove-label`，关闭通过 `gh issue close`；[标签映射](triage-labels.md)使用前核对。
- 多行 UTF-8 草稿放在 `<CRB_TEMP_ROOT>/scratch/crb-<任务>/`，通过 `--body-file` 传入，不拼接进 shell 命令。不提交凭据、个人素材、机器路径或原始日志；路径使用仓库相对路径或 `<CRB_TEMP_ROOT>` 等占位符。
- 写入前分页读全评论；状态评论按标识与 Issue 编号查找，多条匹配时先核对再合并。共享账号不得用 `--edit-last`。修改前通过 `gh api repos/Alexis-Li/Character_Reference_Builder/issues/comments/<评论ID>` 核对 `issue_url`、作者、标识（如有）、正文及 `updated_at`；写入前再读一次并协调并发修改。
- 修改评论通过 UTF-8 JSON 文件和 `gh api --method PATCH ... --input <文件>` 传完整正文。发布后读回正文／标识并记录 URL；超时或结果不明先查询再重试，避免重复评论。同一 Issue 串行写入；已有多人协作时由协调者发布汇总，读后写本身不构成原子锁。
- 草稿在发布核验和必要证据迁入维护位置后按任务归属清理；发布失败保留草稿并说明下一步。

## 归档与清理

仅在用户要求整理或关闭 Issue 时整合评论。除用户缩小范围外，整理／关闭流程包含以下步骤；实际远端写入与删除仍服从当前任务授权。只有规则优化任务时，不据此操作既有 Issue。验收完成、关闭和清理分别如实报告。

1. **盘点。** 分页读取 Issue、全部评论及引用证据，检查任务专属 scratch 和已知输出，确定归属及仍在使用的内容；不遍历清理其他项目的共享临时产物。
2. **迁入有效知识。** 将未来决策或回归检查需要的结论和必要证据并入[既有维护位置](documentation.md#信息归属)，完整产品需求仍在唯一正文。删除无效旧说法；保留影响当前验收的有效决定、缺口和完成条件。必要的仓库内容先在授权内提交、发布并核验可访问性，未发布则保留依赖它的源评论。无需将每条评论完整归档或创建 JSON 包。
3. **整合状态。** 创建或编辑唯一状态评论，链接有效知识、最终审核与验收证据，更新指向待删除评论的现役引用。读回正文并核对链接。关闭时状态为“已关闭”，包含最终集成 SHA；在满足关闭条件并准备执行关闭时更新，若关闭失败则修正为实际状态。
4. **清理。** 按精确 ID 重读目标评论，核对并发修改，在授权内删除状态评论之外的其余评论。清理已不需留存的任务专属临时文件，包括辅助脚本、草稿、载荷和结果；删除前规范化路径并核对任务归属，保留共享、归属不明或仍在用的文件。权限不足或必要内容尚未发布时保留对应对象，说明缺口与下一步。
5. **复核。** 分页确认仅剩一条状态评论，或准确列出未清理对象及原因；检查证据链接、发布状态及最后一次辅助操作产生的临时文件。满足验收与集成条件后显式关闭，不另发关闭评论，并读回实际状态。报告保留／删除数量及未完成事项。

既有历史记录和评论归档文件作为已发布引用的来源继续可用，不为迁移流程回写原文。必要证据不得包含凭据或私人素材；无法安全迁入时保留来源并说明限制。分支／worktree 清理按[分支边界](#分支与交付边界)核对集成、可恢复性与使用状态，不能只看 Issue 已关闭。
